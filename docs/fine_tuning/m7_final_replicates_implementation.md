## 3. Inactive gate

Each YAML has `document_status: M7_IMPLEMENTATION_READY_FOR_REVIEW_NOT_AUTHORISED`, `consumable_by_executable_workflow: false`, every execution flag false, `authorisation_entries: []`, no `authorization_commit` key, and no GPU, UUID, PCI, `CUDA_VISIBLE_DEVICES`, output directory, timestamp, or biological binding. Each static section is compared with the same section built in code, so any drift is refused.

Each entry point accepts `--help` and `--schema` (static schema inspection) and refuses a seed, path, data, model, GPU, learning-rate, or output argument. All three stages also accept `--authorisation-id <id>` and nothing else, and each dispatches to a real launcher (`launch_authorised_entry`, `launch_authorised_candidate`, and, new in revision 4, `launch_authorised_selection`). Revision 3 left the final-selection stage with only `--help` and `--schema`, so M7 could not have been completed without an untracked script; it now has a launcher (section 7).

**Inactive refusal.** With the checked-in inactive configuration the id is parsed, the tracked configuration file is read, and the launcher refuses with `execution_not_authorised`. Nothing else happens first: no directory is created, and the environment, git, a GPU, the interpreter, the run root, an asset, a weight or any biological path is not touched. The tests prove this with every one of those operations patched to fail. A malformed id is refused as `cli_argument_rejected`. Dispatch is therefore implemented but cannot currently execute: a later authorisation-only commit that activates an entry is needed, and no code change, injected callable or monkey-patching is.

**Replicate dispatch (active entry).** The launcher validates the exact configuration schema; locates exactly one entry (unknown, duplicate, inactive, consumed, or already-existing entries fail closed); verifies the seed (the id, scope and entry must agree), the implementation commit, the authorisation commit (the live `HEAD`, never stored) and its single parent; the branch (`main`), a clean tracked tree and index, the remote binding (`origin/main` is the implementation commit or the authorisation commit, read from the local ref without a fetch), the permitted changed-file set (the replicate configuration only), the authorised file hashes at the parent and in the working tree, and the RNAGenesis pin and cleanliness; the physical GPU, logical `cuda:0`, UUID and PCI binding; the output directory and its ancestry; free space; the inherited CUDA selection, `LD_LIBRARY_PATH` and pinned interpreter; and only then consumes that one entry and starts one worker from values sealed in the entry (interpreter path, output directory and id). The seed 43 and seed 44 entries are consumed independently, and a retry needs a new entry with a new id and a new output directory (a document that reuses a failed id or directory is refused).

## 4. Authorisation design (schema only)

A later authorisation-only commit may change only the replicate configuration. It may carry **one or two independently consumable entries, one per seed**. Each entry binds the authorisation id (it must contain `seed43` or `seed44` and equals the output directory name), the seed, the implementation commit (equal to the authorisation parent), physical and logical GPU identity, the exact output directory (a direct child of the run root), the implementation-file, configuration, learning-rate-trace, B1, TRAIN, VALIDATION and validation-artifact hashes, the forbidden M6 weight hashes, and the full expected epoch, update-count and checkpoint-name universe.

Each entry (replicate and candidate) also carries `ld_library_path` (`null` or one exact value, section 5) and `interpreter` (the exact pinned interpreter path with the resolved path, SHA-256 and size of the executable it resolves to, section 5). The inactive configurations bind neither. A candidate entry additionally binds `implementation_config_sha256`, as the replicate entry does, so the same repository-binding check applies, and the predecessor evidence it depends on: `replicate_manifest_path`, `replicate_manifest_bytes`, `replicate_manifest_sha256`, `candidate_seed`, `candidate_epoch`, `candidate_update`, `checkpoint_relative_name` and `checkpoint_weight_sha256` (section 7). No checksum sidecar is used: the byte count and SHA-256 of the manifest itself are the binding.

The launcher accepts only an authorisation id. It resolves one entry, validates it, checks free space, creates and consumes **that entry's own** directory, and starts one worker for one seed. Consuming, failing, or retrying one entry never consumes the other. A retry needs a new entry (a new id and a new directory). A candidate-guardrail entry follows the same pattern, one per candidate, and binds the failed manifests of every earlier-ranked candidate. No active entry exists in this package.

## 5. Replicate loop and engineering behaviour

- A fresh `randperm` is drawn from one dedicated CPU generator at the start of each epoch (five distinct permutation digests recorded). A separate dedicated CPU generator drives diffusion noise. Both are seeded with the training seed; the validation-draw seed `1` stays separate and the draws are loaded, never regenerated.
- After every epoch: checkpoint save and proof, EncDec frozen check, fixed-draw validation. A failed production CUDA RNG read fails closed.
- **Checkpoint proof.** Exclusive direct-child directory; files and directories are flushed; the inventory is exact (four members), symlink-safe along every ancestor, `st_nlink == 1` on every leaf, and on one device; members are hashed with bounded streaming digests (1 MiB chunks, `O_NOFOLLOW`, size, mtime and inode must not change while reading); the tree signature must not change across hashing and reload; the reloaded object must be a fresh object; configuration compatibility is proved before the complete state comparison; a saved weight that equals one of the three forbidden M6 hashes fails the run.
- **Durability.** Atomic writes use an exclusive temporary file, `fsync`, `os.replace`, and a parent-directory `fsync`. Consumption `fsync`s the new directory and the run root.
- **Failures.** After consumption every `BaseException` (including `KeyboardInterrupt` and `SystemExit`) becomes a message-safe record with the seed, epoch, update, microbatch, substage, candidate and partial-checkpoint state (`none`, `directory_created`, `saved_unverified`, `verified`) and the retained epochs. A library message is never copied (only the exception class), and a detail that looks like a sequence is omitted. If the record cannot be written the original error is kept and the secondary failure is reported on it. An existing failure record stays authoritative and a claimed success manifest is removed.
- **Environment.** The child environment is built from an allow-list (`LANG`, `LC_ALL`, `LC_CTYPE`, `TZ`) plus a fixed `PATH` (below), the fixed `CUDA_MODULE_LOADING=LAZY` control (section 11), and bytecode, offline, CUDA device, and isolated `HOME`, temporary, XDG, Hugging Face, torch, Triton, CUDA and matplotlib locations inside the bound directory. A parent holding `PYTHONPATH`, `PYTHONHOME`, `LD_PRELOAD`, any `GIT_*` other than the benign editor and prompt variables, or a credential-pattern variable is refused before consumption. The worker re-checks that its environment is exactly that set. A name outside it is still rejected. The rejection names the stray variables in sorted order, at most eight names, and never their values; a name that is not a short identifier is omitted from the text and still counted.

  **`LD_LIBRARY_PATH` (authorisation-bound, never inherited).** The parent's value is not copied wholesale. An entry carries `ld_library_path`: `null` (the inactive configuration, and any entry that needs none) or one exact string. With `null`, an ambient `LD_LIBRARY_PATH` is dropped and the child never sees one. With a string, the launcher requires the live value to be present and byte-for-byte equal to the binding **before the entry is consumed**; an absent, changed, extended, or empty value is refused with `environment_rejected` (the text never repeats either value), and only the bound string enters the child. The binding is judged on its text alone: every colon-separated component must be an absolute, normalised path with no empty, relative, `..`, space, variable-expansion, REF/EVAL or RNAGenesis-cache component. The worker re-checks the live value against the entry, and the manifest records `environment.ld_library_path = {bound, passed_to_child, sha256}`, where `sha256` is the digest of the exact UTF-8 value (the value itself is not stored). The replicate launcher and the candidate generator both use it. This preserves the known-working M6 runtime, which inherited the parent environment wholesale, without restoring wholesale inheritance: the one variable the pinned runtime needs is carried across only if the authorisation names its exact value.

  **Pinned interpreter.** An entry binds `interpreter = {path, resolved_path, sha256, size}`. The path must be exactly `/home/laura/miniconda3/envs/rnagenesis-h200/bin/python` (the pinned RNAGenesis H200 environment). It may be a symlink (a conda environment's is), but it must resolve to a `python3.8` file inside that environment; the resolution is judged on its text before anything is opened, then the ancestry of the resolved file is walked with `lstat`, the leaf must be a regular non-symlink file, and its size and SHA-256 are taken and rechecked. Hard links are recorded and allowed for the interpreter, since a conda environment hard-links its files. Before consumption the launchers compare the observation with the binding and refuse any difference (`interpreter_rejected`, without repeating either identity); the replicate worker and the candidate producer compare again; the child is started with the bound path; and both manifests record the identity under `environment.interpreter`. The observation is a function that tests replace with a mock. The pinned interpreter itself ran every test suite in preparing this package; what is mocked is the M7 interpreter-identity observation (path resolution, SHA-256 and size of the resolved file) and the authorised launch of a child with it, so no authorised child was started and no real identity was read or bound.

  **Fixed child `PATH`; absolute `git`, `nvidia-smi` and Python (revision 4).** Revision 3 copied the parent `PATH` into the child and started `git` and `nvidia-smi` by name, so a shadowing directory early on the invoking shell's `PATH` could have substituted either tool. The child `PATH` is now the constant `FIXED_CHILD_PATH = <pinned environment>/bin:/usr/bin:/bin` and parent `PATH` text is never copied (`PATH` is no longer in the allow-list; the worker check requires exactly the constant). The pinned environment's `bin` directory comes first so a by-name lookup made by the pinned interpreter finds that environment's own tools; `/usr/local/bin` and every ambient directory from the invoking shell are absent. The only user-space `PATH` component is the deliberately pinned environment. `git` and `nvidia-smi` are located at the fixed paths `/usr/bin/git` and `/usr/bin/nvidia-smi` (found by read-only path inspection; `nvidia-smi` was never executed) and are invoked only through `run_trusted_tool`, which refuses any other path before touching the filesystem, then validates by `lstat` alone that `/usr`, `/usr/bin` and the tool are root-owned, not group- or world-writable, not symlinks, and that the tool is a regular executable file; it runs the tool with `shell=False`, a fresh environment (`PATH` fixed, `LANG=LC_ALL=C`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`; nothing copied from the parent) and no standard input. A `git` failure never echoes git's own text. Each launcher also replaces the `PATH` of its own process by the constant after its inactive gate and parent-environment check, so accepted upstream code that still starts a tool by name resolves it through the fixed directories. The accepted B1 and M6 files are unchanged: the M7 replacements reuse the B1 parent-CUDA check, query arguments and probe parser, and a test shows the M7 probe returns exactly what the accepted M6 and B1 probes return on the same output. Every child command must start with the absolute pinned interpreter (`assert_pinned_interpreter_argv`), and a static test shows that the only process starts in the M7 sources are the trusted-tool runner and the pinned worker spawn.

  **Symlink-safe inspection.** Candidate inputs and assets are never followed silently. For every required file the ancestry is walked with `lstat` (every component a real directory), the leaf must be a regular, non-symlink file, the size is checked against its pin, the signature (size, mtime, inode, device, link count) is taken before the file is hashed or read, the hash streams through `O_NOFOLLOW`, and the signature is rechecked afterwards; a change, a swap for a link, or a missing file fails closed (`asset_inspection_unsafe`). *Hard-link and device policy:* the single-hard-link rule (`st_nlink == 1`, same device) applies to evidence this package writes and consumes, namely checkpoint members (the strict tree) and the sealed replicate manifest; the external pinned assets (the RNAGenesis model files, the cleaner, the Diffusers patch, the interpreter) and the accepted schedule and TRAIN files may be hard-linked, and their link count is recorded and rechecked. This covers the generation inputs, the frozen EncDec assets, the Diffusers patch, the cleaner and metrics sources, the accepted length vector and schedule, TRAIN, and the replicate manifest. The M6 asset observer that the replicate launcher still calls before consumption is M6 code and was not changed (section 10).
- **GPU identity.** The worker compares logical `cuda:0`, device count one, `CUDA_VISIBLE_DEVICES`, physical index, UUID and PCI bus with the entry before any biological open. The real identity read (`PinnedReplicateStack.observe_gpu_identity`, which now uses the M7 absolute-path `nvidia-smi` probe `common.live_gpu_probe`) is not exercised without a GPU.
- **Free space.** The budget is integer arithmetic: five checkpoints of the B1 weight size plus 4 MiB, a 2 GiB log allowance, ten percent, and a 20 GiB reserve. It is checked by the launcher before consumption and by the worker, and recorded in the manifest.
- **Path denial.** REF and EVAL (any case, Unicode-folded, any token spelling), obsolete repository-local data, M6 and sibling evidence, and any path other than the role's pinned location are refused on the path text and its resolved form before a filesystem open. The accepted validation-artifact directory is the only run-root input.

## 7. Candidate guardrails and selection

Candidates are evaluated in the order of the sealed ranking until the first pass. `lazy_plan` refuses a non-prefix evaluation, an evaluation after the first pass, and an incomplete evaluation. If every candidate fails, the outcome is `no_eligible_checkpoint`; the learning rate, thresholds, architecture and seed are never changed automatically. The selection stage rejects seed 44 alone, a missing seed without the deviation, duplicate or unexpected seeds, mismatched B1 initial-state digests, inconsistent validation-artifact identities, extra, missing or duplicate epoch candidates, selection from update 0, selection from an unevaluated or failed candidate, a non-prefix evaluation, and any REF or EVAL derived input. `validate_final_selection_manifest` re-derives every selection claim from the embedded tables (revision 4; revision 3's docstring claimed this but several fields were not checked): exact key sets for every nested record, the SHA-256 shape of every digest, integer (not float or bool) seeds, epochs and ranks, type-strict comparison of every fixed block, exact replicate and guardrail index rows (no duplicate, missing, extra or out-of-order entry; the guardrail index must equal exactly the evaluated candidate rows), recomputation of every `ranking_sha256` over the replicate-style ranking record rebuilt from the candidate table, the seed status derived from the lazy trace (`selected` only for the first passing evaluated candidate, `no_eligible_checkpoint` only when all five were evaluated and failed), every checkpoint member name and digest bound between the candidate row and the selected row with the weight member equal to the weight hash, and the replicate hashes bound between the index, the seed records and the deviation record. What it cannot do is refute a self-consistent rewrite, because the manifest does not contain the replicate or guardrail bytes: `selected_set_sha256` is a deterministic content hash, not an authenticity mechanism, and `rebuild_matches` (which rebuilds the manifest from the sealed input bytes and compares) is the check that shows a manifest is what those inputs produce. `launch_authorised_selection` invokes the deterministic builder as a dry run before consumption; after consumption it invokes the builder again, validates the result and writes it atomically. It does not itself call `rebuild_matches`, which provides the corresponding byte-for-byte comparison for later audit.

**Production generation callable (implemented).** `production_generate_and_measure` is the default of `run_candidate`, so an active entry needs no injected callable. It is called after the bound directory is consumed and the checkpoint tree and member hashes are verified, and the checkpoint is verified again afterwards. It reuses the accepted M6 diagnostic module (loaded by its tracked path, unmodified) and the hash-verified B1 runner, M4 metrics and approved M1 cleaner:

1. **Predecessor evidence is reopened and validated before consumption.** The launcher (and the producer again after consumption) opens the exact bound `m7_replicate_manifest.json` beside the checkpoint through the symlink-safe, single-link inspection. It must have the bound byte count and SHA-256, be canonical JSON, have exactly the replicate-manifest key set, pass the independent replicate-manifest validator, and have reached a successful terminal state (`replicate_completed`, `consumed_successfully`, no warnings, the replicate closure). Nothing copied into the candidate entry is trusted unless it agrees with it: the seed; the B1 initialisation (accepted weight and configuration hashes, loaded fresh, no M6 checkpoint); the validation-artifact identities; the epoch, the update (epoch-end, never 0), the checkpoint's relative name, member hashes and weight hash; the five epoch checkpoints; and the entry's ranking position and failed earlier candidates as the prefix of the sealed ranking with the bound ranking hash. Update 0, M6 evidence, a sibling replicate and any unlisted checkpoint are refused. Only after this does the launcher consume the entry; TRAIN, the model assets and the checkpoint weights are opened after consumption.
2. `LD_LIBRARY_PATH` match, then the pinned generation inputs and frozen EncDec assets are hashed against their pins.
3. The accepted schedule is rebuilt from the accepted length vector and compared byte for byte: 1,000 attempts in 112 invocations, invocation seed `44000 + invocation_index`, `max_seq_len = requested length + 1`, chunks of at most 16.
4. TRAIN is opened once, after consumption, for the exact-copy guardrail only (hash, count and lengths checked). VALIDATION is not requested; REF and EVAL are refused by role and by path text, in the resolved form too, before any filesystem access.
5. All 112 invocations run in schedule order through `generation.py` with only `--dm_file` substituted by the authorised checkpoint, in the allow-listed child environment. Nothing is retried, resampled, replaced, truncated, padded, dropped, or deduplicated. A failure stops the run and the failure record names the invocation index and the sub-stage (`generation_invocation_command`, `_spawn`, `_output_read`, `_output_mapping`).
6. The 1,000 attempt rows are checked (exact field set and order, no malformed, missing, duplicate, excess or unscheduled row, schedule fields equal, normalisation reconciled with an independent restatement of the cleaner rule). Invalid, empty, duplicate, early-EOS and length-mismatched attempts all stay in the denominators.
7. The five numerical guardrails come from the accepted M4 evaluation and are cross-checked against the M7 decisions. Requested-length matching, early EOS and gross length behaviour (including a count of valid outputs below half the requested length) are report-only with no threshold.
7a. **Report-only M6 diagnostics, reused unchanged.** The accepted `report_only_diagnostics` of the M6 diagnostic module (pinned by the implementation hashes) runs on the full 1,000-attempt ledger: requested-length exact-hit rate, early-EOS and length-mismatch accounting, nearest-TRAIN normalised edit distance, the maximum edit similarity to TRAIN, nucleotide and dinucleotide total-variation distance to TRAIN, MFE, MFE per nucleotide, paired fraction, and the per-requested-length strata. They are written to `m7_candidate_report_only_diagnostics.json`, bound by hash, and summarised by a headline in the manifest. Edit similarity is `1 - normalised edit distance`, an edit-based similarity that is **not** sequence identity. None of this is a threshold and none of it enters the ranking or the five guardrails; every raw attempt stays in its denominator. The folding library is probed before consumption.
8. Raw and normalised ledgers, the invocation manifest, metrics, guardrail values and the schedule copy are written atomically and bound by hash in the manifest. Raw checkpoint weights only; no EMA.

`launch_authorised_candidate` (reachable through `--authorisation-id`) resolves one id to one entry, validates the active document, binds the repository (branch, remote, single parent, authorisation-only delta, implementation hashes, RNAGenesis pin and cleanliness), matches `LD_LIBRARY_PATH`, the pinned interpreter, the parent CUDA variables and the GPU identity, probes the folding library, reopens and validates the predecessor evidence, refuses a seed and epoch that already has a success manifest elsewhere, and only then consumes the entry. The candidate stage never accepts update 0, an epoch outside 1 through 5, an unexpected seed, a checkpoint not listed in the sealed replicate manifest or whose identity differs from it, an M6 checkpoint or evidence path, a sibling replicate's checkpoint, or an already consumed or evaluated candidate authorisation. `build_candidate_argv` reuses the accepted B1 invocation contract with exactly one substitution, `--dm_file`.

The real run, with real weights, a GPU, TRAIN and the accepted schedule files, has not been exercised: the tests below use a synthetic world (section 9).

## 10. Residual limitations and deferred findings

1. **Hash-to-open TOCTOU (documented, not solved).** A path is hashed and later opened by name. Detection exists only where a signature is compared across the open (the streamed digest and the checkpoint tree). A file replaced between a separate hash and a later load is not detected.
2. **The production candidate generator has not run for real.** It is exercised end to end only against a synthetic world. The first real run will be the first time the real `generation.py`, the real weights, TRAIN, the accepted length vector and schedule, and the multi-gigabyte EncDec hashing meet this code. Hashing the EncDec assets is repeated for every evaluated candidate (up to five per seed); it is not optimised.
3. **GPU identity collector.** `observe_gpu_identity` and the candidate preflight read `nvidia-smi` (now by its absolute, validated path, revision 4) and cannot run without a GPU; only their comparison logic, argv and environment are tested, and the M7 replacements are shown to return what the accepted M6 and B1 probes return on the same text. `nvidia-smi` was never executed in preparing this package. The accepted M6 and B1 files still start it by name; the M7 launchers never call them for that.
4. **The `LD_LIBRARY_PATH` value to bind is not chosen here.** The mechanism is complete and tested (section 5). The exact value of the known-working M6 runtime was deliberately not read in this package, so the authorisation package must observe it on the pinned runtime and bind that exact string, or bind `null` if the runtime needs none.
5. **Same-device and link checks are made on Linux.** They are applied unconditionally; a filesystem that reports a constant `st_dev` would pass trivially.
6. **Reload digest cost.** Each epoch hashes the full state twice (about 7.8 GB each) on the CPU, as the M6 comparison did for three checkpoints; the wall-clock cost of five has not been measured.
7. **The two seeds share one dedicated seed value** for the permutation and diffusion generators (the accepted M6 convention). The streams are distinct objects and their final digests are recorded.
8. **Launch convention.** As in M6, the human launches with `CUDA_VISIBLE_DEVICES` and `CUDA_DEVICE_ORDER` already set to the authorised physical GPU index and `PCI_BUS_ID`, because the parent GPU probe requires them and a conflicting inherited value is refused.
9. The tracked YAML records a learning-rate trace hash computed with `math.cos` on the pinned interpreter; another libm could in principle round differently, and the contract then refuses to run (fail closed).
10. **The replicate launcher is wired, but never run for real.** It dispatches only against mocks; the live repository observation (`git` calls, including `origin/main` read from the local ref), the `nvidia-smi` GPU probe, and the real worker spawn have not been exercised. The M6 asset observer (`observe_required_assets`) and the M6 pinned-Python helper it calls before consumption are M6 code and were not changed or hardened against symlinked ancestors.
11. **Predecessor evidence is verified, not predecessor manifests of failed candidates.** The candidate launcher reopens and validates the replicate manifest and checks that the entry's failed predecessors are the prefix of the sealed ranking, but the hashes of the failed earlier candidate manifests are still verified only by the final-selection stage, which sees every manifest.
12. **Strict ancestry may refuse a real run that M6 accepted.** Asset ancestry is now walked with `lstat` and any symlinked directory in the path (for example under RNAGenesis or the conda environment) fails closed, where the accepted M6 diagnostic checked only the leaf. This was not observed on the live system; if a pinned path legitimately crosses a symlink, the authorisation package must bind the real path instead.
13. **Hard-link policy is split.** Single-link is enforced for checkpoint members and the sealed replicate manifest; external assets, TRAIN, the schedule files and the interpreter may be hard-linked (a conda environment's are), with the link count recorded and rechecked. A hard-linked pinned data file is therefore not refused.
14. **The interpreter identity is a path-resolution and file-identity binding.** It does not prove that the running process loaded the bound file (it relies on the child being started with the bound path), and the bound SHA-256 and size must be observed on the pinned runtime at authorisation time; they were not read here.
15. **Nearest-TRAIN and MFE diagnostics are computed after consumption** and cost CPU time in proportion to 1,000 attempts times 669 TRAIN records; the folding library is only probed (not run on real input) before consumption. No sidecar checksum file is used for the replicate manifest.
16. **The final-selection launcher has never run for real.** It runs only against temporary synthetic manifests. The live repository observation (the absolute `git` calls) and the real `/usr/bin/git` path inspection were exercised only for a read-only `rev-parse`; the first real selection will be the first run through the live observation and a real run root.
17. **The selection runs under the pinned interpreter by resolved path only.** Unlike the replicate and candidate entries it binds no interpreter hash, size or `LD_LIBRARY_PATH`: it is standard-library-only, creates no child process, and its code and the files it loads are bound by the implementation file hashes. The check compares the resolved path of the running interpreter with the pinned one and executes nothing.
18. **A final manifest proves internal consistency, not authenticity.** `validate_final_selection_manifest` re-derives every embedded claim, but a self-consistent rewrite of the candidate table and the selected set (including a non-weight member hash) is accepted by it. The launcher runs the deterministic builder over the bound input bytes as a dry run before consumption and again after it (validating and writing the result), and `rebuild_matches` provides the corresponding byte-for-byte comparison for any later audit; `selected_set_sha256` is a content hash, not a signature.
19. **The inputs are hashed and read by name.** The documented hash-to-open window applies to the bound manifests too: they are inspected by `lstat` and rechecked after the read, but a file swapped between inspection and `open` by an actor who also reproduces its size, mtime, inode and link count is not detected. The tool paths `/usr/bin/git` and `/usr/bin/nvidia-smi` are validated by `lstat` before each run in the same way, and a package-manager upgrade of either tool changes the file but not the check.
20. **The fixed `PATH` and the trusted tools are specific to this machine.** `/usr/bin/git` and `/usr/bin/nvidia-smi` were located on this host (Debian-style layout, `/bin` a symlink to `/usr/bin`); a different host needs different constants, and `git` reads the repository's own configuration (but not a user or system configuration, which the tool environment switches off).
21. **Attempt 1 failed before any scientific step, and attempt 2 has not run.** The cause and the contract correction are in section 11. The real worker has not been run again after the correction. A future PyTorch that assigned a value other than `LAZY` would fail closed. Attempt 1 cannot be resumed.

## 11. Attempt 1 and the fixed `CUDA_MODULE_LOADING` control

On 7 October 2026 the single-use authorisation `m7_d1_final_replicate_seed43_e682cb6064a5_gpu1_attempt1` was consumed and failed. The evidence directory `/home/laura/rnagenesis-mres-runs/m7_d1_final_replicate_seed43_e682cb6064a5_gpu1_attempt1` is retained as failure evidence. This corrective package does not modify, rename, remove, reuse or resume it.

The failure record is `authorization_failure.json`, SHA-256 `2612bcbcc8aa3f9273ad51ce00ad3d8524f16b08298d1e31637ce4c39f29c722`. The consumption record is `authorization_consumption.json`, SHA-256 `d99177aee5c719082bfcc79d1a9d3c1f639c63ea44b7470cf4d877b0b982eb15`. The code is `environment_rejected` and the stage is `runtime_identity`. The detail written by that attempt is `the worker environment holds 1 names outside the allow-list`. The state is consumed, failed and non-resumable. Epoch, update, microbatch and the partial checkpoint are null, `retained_checkpoint_epochs` is empty, and there is no scientific success manifest. `scientific_run_completed` and `m7_complete` are false. The authorisation commit is `efa118dee886fa29e66626170dba9467b10e72c3`. Its parent, and the executing implementation commit, are `e682cb6064a578868cc258e58465a0c036afe0d4`. The post-failure observation supplied with that attempt is that GPU 1 remained at 15 MiB used and 0% utilization. This package did not query the GPU again.

No biological input, training update or checkpoint was reached. The worker had created its isolated runtime directories and had imported the training stack far enough for CUDA synchronization to run; the failure is the environment check immediately after that synchronization.

Root cause, confirmed from the installed pinned PyTorch source by read-only inspection and not by initializing CUDA:

1. The import-only diagnostic passed with no environment change.
2. `run_authorised_replicate` then calls `clock.stamp()`.
3. `SynchronizedClock.stamp()` calls `torch.cuda.synchronize()`.
4. Pinned PyTorch `2.1.2+cu121` (`torch/version.py` in the `rnagenesis-h200` environment) assigns `CUDA_MODULE_LOADING=LAZY` inside `torch.cuda._lazy_init` when the variable is absent, and it does so before `torch._C._cuda_init()`.
5. M7 then calls `assert_child_environment`, which rejected the new name because it was not in the worker allow-list.
6. This is before biological inputs, training updates and checkpoints.

The correction is a named fixed child-environment control, `FIXED_CHILD_ENVIRONMENT_CONTROLS = {"CUDA_MODULE_LOADING": "LAZY"}`. `build_child_environment` assigns that value itself after every other child assignment. It does not read or copy an ambient parent value, and a parent value cannot replace `LAZY`. `assert_fixed_child_environment_controls` requires the name to be present and the value to be exactly `LAZY`. A missing name, a non-text value, an empty value, a differently cased value, and any other value fail closed. The observed value is not repeated. The worker allow-list includes the name only after that check. An unexpected name is still rejected. The diagnostic now reports the count and the sorted names, at most eight, and never the values; a name that is not a short identifier, or that looks like sequence text, is replaced by `<omitted-name>` and still counts as stray.

The null `LD_LIBRARY_PATH` behaviour, the fixed `PATH`, `CUDA_VISIBLE_DEVICES`, `CUDA_DEVICE_ORDER=PCI_BUS_ID`, the offline controls and the isolated cache paths are unchanged. The clean-repository, GPU, interpreter, asset, data-access and single-use gates are unchanged.

`config/experiments/D1_final_replicates.yaml` is returned to the inactive implementation document: no authorisation entries, every execution flag false, and no GPU, interpreter, output, timestamp or attempt-2 binding. Scientific hyperparameters, the seed policy, the M8 total of 30,000 raw D1 attempts, and retention through at least 1 November 2026 are unchanged. This is an implementation-contract correction, not a change to scientific hyperparameters or evaluation policy.

Attempt 1 is non-resumable. Attempt 2 requires a new implementation commit, a new authorisation id, a new output directory, and a separate approval. This package does not create that authorisation, that directory, or that command.
